Agent 做不成事，多数时候不是模型不行，是它外面那层工程结构没搭起来。

## 0. 为什么写这篇文章

现在关于 agent 的内容大致分两类。一类是“三十分钟做一个 XX 助手”，跑通即结束；另一类是框架选型对比，讲的是工具而不是方法。这两类都跳过了同一件事：一个 agent 从“能跑通一次”到“敢交给它干活”，中间隔着什么。

本文想说清楚的就是这中间的部分。它不是框架选型指南，也不教调提示词。

面向刚接触 agent 的人。默认你没用过 agent，但知道什么是函数、什么是文件夹。

关于出处：文中引用的观点集中标在附录 A。没标出处的地方是我自己的判断或推断，会写明“我的做法”“这条我没把握”之类，你可以不同意。所有具体数字——样例要凑多少个、置信度阈值划在哪——都是拍的，给你一个起点而已，不是标准。

## 1. 先把几个词说定

- **Agent（智能体）**：能自己决定“下一步调用哪个工具”的程序。和普通脚本的区别是，脚本的步骤你写死，agent 的步骤它会自己选。
- **提示词（prompt）**：你写给模型的那段指令。
- **上下文（context）**：模型这一次思考时能看见的全部文字。除了提示词，还包括它读到的资料和前几步的结果。它没有记忆，你不给它，它就不知道。
- **工具（tool）**：你写好的一段函数，开放给 agent 调用。比如“读某个 PDF”“往表格里加一行”。
- **Token**：模型处理文本的最小单位，中文大致一个字对应一到两个。上下文长度按 token 算。

全文用一个例子贯穿：把一个文件夹里的 183 张 PDF 发票整理成一张对账表（`recon.xlsx`）。每行有 5 个从发票上抽出来的字段——发票号、开票日期、销售方、金额、税额，另加两列由规则填写的状态和备注。

这活儿不难，但足够真实：格式不统一，有扫描件，有重复，有作废。

## 2. 任务边界：窄到能算出一个等式

任务边界就是把“要做什么”写到只剩一种理解方式。

“帮我处理一下财务”不是边界。“读 `invoices/` 下所有 PDF，每份抽 5 个字段追加到 `recon.xlsx`，读不出的移到 `unresolved/` 并在末尾列清单”才是。

### 窄边界为什么反而好办

直觉上限制越多能力越受限，对 agent 恰好相反。原因有两条，一条关于它做得更准，一条关于你更容易把它改准。

第一，它每一步都在做选择题，可选动作越少选错概率越低。这里有个容易忽略的点：可选动作不由任务描述决定，而由你给它的工具和权限决定。任务写得再窄，手里挂着五十个工具照样有五十个岔路；写了“不许联网”却留着联网工具，等于没写。边界要同时落到两处，一份给它看的任务描述，一份它真正能碰到的工具清单。

第二，出错时你知道该改哪儿。范围大的任务失败了你只知道“它不行”；范围小的任务失败了，你知道是手写体金额没识别出来。

| 对比项 | 坏边界 | 好边界 |
| --- | --- | --- |
| 任务描述 | 帮我整理发票 | 读 `invoices/*.pdf`，抽 5 个字段写入 `recon.xlsx` |
| 输入范围 | 没说 | 只读 `invoices/` 一层，不进子目录 |
| 特例规则 | 没说 | 重复票只保留一行，备注列注明被跳过的原文件名；作废票照写，状态列填“作废”且不计入合计 |
| 完成标志 | “整理好了” | 写入行数 + 跳过的重复数 + `unresolved/` 文件数 = PDF 总数 |
| 禁止动作 | 未定义 | 不删原文件、不改已有行、不联网 |

注意“特例规则”那一行。重复票和作废票怎么处理，不写清楚，“完成标志”那一行的等式就对不上，后面第 6 节也没法为这两类样例定出正确结果。

**边界要划到能算出一个等式为止。** 这是我判断边界够不够窄的唯一标准——如果你写不出验收条件，说明还没划清，别往下走。

### 顺带一个前置问题：这活儿真需要 agent 吗

Anthropic 把 workflow 和 agent 分开定义：workflow 是“由预先写好的代码路径来编排”的系统，agent 则“自己决定流程和工具调用”。前者可预测、便宜、好排查，后者灵活但更贵，而且错误会一步步累积。

我的做法是，步骤能提前写死就写死。发票这个例子里，“遍历文件 → 抽字段 → 写入表格”是固定的，真正需要临场判断的只有“这张 PDF 看不懂时怎么办”。所以外层用固定流程，只在难点上放 agent。这样出问题时还能一眼看出是流程写错了还是 agent 判断错了。

## 3. 上下文：删掉、按需取、核对来源

上下文窗口（模型一次最多能看多少字）越做越大，很多人的做法就变成了能塞就塞。但模型的注意力是有限资源。

Anthropic 引用过一个叫 context rot 的现象：上下文越长，模型从里面准确回忆出某一条信息的能力就越差。不是它读不懂，是它容易漏看、记串。原因之一是注意力像一份有限预算，每多一个 token 就从这份预算里分走一点。他们给出的目标是找到 “the smallest possible set of high-signal tokens”，能达成目标的、最少的那批真正管用的信息。

给它一页写得准的资料，比给它十页什么都有的资料有效。省下的钱是顺带的，真正省的是它的注意力。

具体三个动作。

**删掉无关的。** 183 张发票的全文不该进上下文。该进的是字段口径（“金额”指含税总额还是不含税那一栏）、公司名称的别名表（“XX 科技”和“XX 科技有限公司”算同一家）、一张人工确认过的样例。

**按需取，不预先全给。** 给它文件清单和一个“读第 N 张”的工具，让它需要哪张读哪张。Anthropic 把这叫 just-in-time 检索，类比是人不会背下整个资料库，人记的是目录和位置。代价是慢一点，换来的是每一步的上下文都干净。

**必要时主动搜，并且核对来源。** 涉及时效性的信息——税率、政策、接口文档版本——模型训练数据里的那份可能已经过期。让它去查，但要有约束：优先一手来源而不是二手转述；记录来源和日期写进产出物，人能回查；关键数字要有两处独立来源对得上，对不上就标出来交给人，不要挑一个看着对的。

最后这条是我踩过之后才当回事的。Agent 有一类错误特别难查，它给出一个格式完美、来源虚构的答案。要求它带出处，等于给了你一个成本很低的抽查把手。

| 该进上下文 | 不该进 |
| --- | --- |
| 字段定义、口径说明 | 原始文件全文 |
| 边界与禁止动作 | 与本次任务无关的历史对话 |
| 一两个确认过的正确样例 | 十个风格不一的样例 |
| 上一步的结论（一两句话） | 上一步完整的工具返回 |
| 可回查的来源链接 | 记不清出处的“经验” |

## 4. 工具：输入、输出、权限、失败

Anthropic 有个说法：工具是确定系统和不确定的 agent 之间的一纸约定。相比之下，普通接口（两段程序之间约好的调用方式，比如你的程序调支付宝的收款接口）是两个确定系统之间的约定。差别就在“不确定”三个字上——调用工具的这一方会猜、会填错参数、偶尔会编造一个不存在的字段。所以工具的设计要求比普通接口更高。

**输入**要少、要严，约束写进定义。日期就规定 `YYYY-MM-DD`，别接受“随便什么格式”。能给固定选项就别让它自由填写，比如状态字段只允许填“正常”或“作废”（这叫枚举），填别的直接报错。把错误挡在调用之前，比调用之后再处理便宜得多。

**输出**要它看得懂。下面这种写法叫 JSON，程序之间传数据的常用格式，一对花括号装一条记录，每项写成“名字: 值”。

如果工具只返回 `{"id": "7f3a91c"}`，agent 没法据此做任何判断。返回下面这样，它才能决定是继续还是交给人：

```json
{
  "发票号": "04321177",
  "开票日期": "2026-03-01",
  "销售方": "XX 科技有限公司",
  "金额": 1200.00,
  "税额": 138.05,
  "置信度": 0.62,
  "备注": "金额区域为手写"
}
```

置信度是工具自己给出的把握程度，0 到 1，0.62 大致相当于“我猜是这个数，但没什么把握”。这个数不需要多准，用处是让把握低的那些行能被单独拎出来给人看。Anthropic 的说法是，agent 处理自然语言名称的能力显著强于处理无意义的标识符——所以别只返回 id。

**权限**要标清楚每个工具能动什么。我一般分三档（这个分法是我自己的习惯，不是什么标准）：

| 档位 | 例子 | 处理方式 |
| --- | --- | --- |
| 只读 | 读 PDF、查汇率 | 直接放开 |
| 可写但可撤销 | 追加表格行、写草稿 | 放开，留操作日志 |
| 不可逆 | 删文件、发邮件、付款、改线上数据 | 必须过人工确认 |

发票这个例子里，agent 根本不需要删除文件的能力。不给，比给了再防要可靠得多。

**失败**信息是写给 agent 看的，它要能据此改正。`Error 422: invalid parameter` 它只能瞎试；`日期格式应为 YYYY-MM-DD，收到的是 "2026/3/1"，请转换后重试` 它一次就能改对。区别在于后者把“下一步该干什么”直接写进了错误里。

还有一条：工具宁可少，不要重叠。如果一个熟悉业务的人看着工具列表也选不出该用哪个，agent 只会更糟。办法是合并同类项——与其提供“查空闲时间”和“创建日程”两个工具让它自己拼，不如直接给一个“安排会议”。

## 5. 人工确认：关卡设在哪，比设几个重要

这一节我想少讲点道理，多讲个场景。

假设发票都抽完了，agent 准备写入 `recon.xlsx`。它可以直接写，也可以先停下来问你一句。选哪个？

如果每一步都要你点一下，agent 就退化成一个很慢的手动工具，没有意义。但如果一步都不问，等你发现它把整张表的日期列填成了发票号，已经写完 177 行了。

所以问题不是要不要设关卡，是设在哪。我的判据是三条，命中任意一条就设：这个动作撤不回来吗（删除、覆盖、付款、提交）；外部能看见吗（发邮件、发消息、改线上数据）；代价会随规模放大吗（一张错了是小事，183 张一起错就是事故）。

按这个判据，“读 PDF”和“写入本地新表格”都不设卡，“把对账表提交给财务系统”必须设卡。

还有一个习惯成本极低但拦住的事故最多：批量之前先跑三五张给人看一眼。它拦的不是随机出错，而是从第一张起就系统性地理解错了某个字段——这类错误一旦批量跑完，返工成本比重新做一遍还高。

设了卡还要注意，弹一个“确定要继续吗？”等于没设，人会闭着眼睛点是。有效的确认长这样：

```text
即将写入 recon.xlsx，共 177 行
  其中 11 行置信度低于 0.7（已标黄）
  6 行状态为“作废”，不计入合计
  2 张为重复票，已跳过，原文件名记入备注列
  4 张 PDF 未能识别，已移入 unresolved/
  金额合计 ¥1,284,300.00
  张数核对：177 + 2 + 4 = 183，与目录内 PDF 数一致
继续？ [是] [否] [只写高置信度的 166 行]
```

标准很简单，人在几秒内能判断该不该点。给的是数字和差异，不是过程复述。

最后还有一类情况人根本轮不上点头——它自己在那儿转圈。这时候要靠自动停止条件：最大步数、超时、连续失败次数上限、单次任务的费用上限。给 agent 设这类上限是常见做法，Anthropic 也把它列为保持控制的手段之一。没有刹车的 agent 出错时会一直错下去，而且账单还在涨。

## 6. 评测：三层，大多数人只做中间那层

这是我认为最容易被跳过、也最不该跳过的一节。

先说为什么必须有评测。Agent 每一步都带随机性，同一个输入跑两次未必走同一条路。你手动试通一次，只能证明存在一条成功路径，不能证明下次也能成。而且改动的影响不可预测，你改一句提示词修好了 A 类错误，很可能同时弄坏了 B 类。没有可重复的测试，每一次“优化”都是在赌。

评测分三层，从外往里问：

**第一层，这件事值不值得做。** 这个任务自动化之后，省下的时间够不够抵掉核对它的时间？有没有更笨但更稳的办法（比如让开票方统一模板）？这一层不需要写代码，但它决定后面两层有没有意义。

**第二层，它做对了没有。** 这是技术评测，也是唯一大多数人会做的一层。不需要平台和框架，三样东西就够：二三十个真实样例（必须包含难例，扫描件、手写金额、作废票、重复票，全是干净样例的测试集没有意义）；每个样例的标准答案，也就是这份输入正确的输出应该长什么样，人工标一次长期复用——标不出来说明第 2 节的规则还没写全，回去补；一个评分脚本，批量跑完输出成功率和失败清单。

顺序上有个建议：评测先于优化。先有分数，再改东西。Anthropic 在讲工具设计时给的建议也是先生成大量贴近真实用法的评测任务，再据此改工具。

只看最终对不对是不够的，四个指标配合起来才有诊断价值：

| 指标 | 看什么 | 说明什么 |
| --- | --- | --- |
| 任务成功率 | 完全正确的样例占比 | 能不能用 |
| 人工介入率 | 需要人返工的比例 | 省不省事 |
| 平均步数与成本 | 单个任务的调用次数、花费 | 划不划算 |
| 失败类型分布 | 错误按原因分类计数 | 下一步该改哪儿 |

第四项最容易被跳过，但只有把失败归了类，你才知道该回到哪一环。另外，每发现一个新的失败案例就把它加进测试集，永远留着。这个集合会越滚越大，作用是让同一个错误在再犯的当天就暴露，而不必等用户来告诉你。

**第三层，有没有人真的用。** 自己的测试集只能证明“在我定义的任务上它做对了”，证明不了这个任务本身值得做。要看真实用户的行为而不是评价：他们会不会用第二次，有没有绕过你的工具自己手动干，在哪一步停下来接管。后两条更难作假——用户通常不会告诉你“你这个不好用”，他们只是不用了。

这三层的顺序是从外往里的，但实际做的时候，大多数人从第二层开始，做出一个技术上正确、却没人要的东西。我自己也犯过这个错。

顺带说一个数字陷阱：内部成功率 95% 听着高，但如果你分不清是哪 5% 错了，人就得每张都复核一遍，省下的时间又还回去了。

## 7. 闭环怎么转起来

这五个环节是一个循环，不是一次性流程。它们的依赖关系是实的：边界决定了评测能不能写出判据，上下文和工具决定了 agent 每一步的选择空间，确认决定了错误能不能在扩散前被拦住，而评测的产出不该只是一个分数，还应该是一份“该回去改哪一环”的指引。

下面这张表是我自己排查时在用的，属于经验总结，没有出处：

| 症状 | 大概率是哪一环 | 怎么改 |
| --- | --- | --- |
| 做了完全没让它做的事 | 边界 | 禁止动作写进任务描述，同时收窄工具权限 |
| 遇到没见过的情况就乱猜 | 边界 | 特例规则没写全，补进任务描述 |
| 反复问已经说过的信息 | 上下文 | 关键结论显式保留，别指望它从长历史里翻出来 |
| 引用了不存在的规定或数字 | 上下文 | 要求带来源，关键数字双来源核对 |
| 选错工具、来回试 | 工具 | 工具太多或职责重叠，合并、改名、写清用途 |
| 卡在同一个错误上反复重试 | 工具 | 报错没告诉它怎么改，把正确格式写进错误信息 |
| 一直重试停不下来 | 确认（刹车） | 没有自动停止条件，加失败次数、步数、费用上限 |
| 出了事故才发现 | 确认 | 关卡位置错了，挪到不可逆动作前面 |
| 每次表现都不一样，说不清好坏 | 评测 | 没有测试集，先补这一步 |

这张表的用法是，不要在症状层面调提示词。“它老是出错”没法修，“它读扫描件时把日期抽成了发票号，20 个样例里错了 7 个”才能修。

## 8. 给新手的核心建议

如果你要从零做第一个 agent，按这个顺序走：

1. 写下任务的验收条件，包括特例怎么算。写不出来就先别做。
2. 想清楚哪些步骤能写死。写死它们，只把真正需要判断的那一步交给 agent。
3. 列出它需要的工具，每个写清输入、输出、权限、失败四栏。
4. 找出所有不可逆动作，在它们前面加确认，同时设好步数、失败次数、费用上限。
5. 从真实数据里挑二十来个样例，标好答案，跑一遍，记下分数。
6. 改一个地方，重跑，看分数变化。

第 5 步是分水岭。跑过一次分之后，“这个改动到底是变好了还是变坏了”才第一次成为一个能回答的问题。

## 9. 结语

这五个环节里，边界、上下文、工具属于设计，确认属于运行时防线，评测属于反馈。三类东西性质不同，但缺任何一类，剩下的都撑不住：没有边界，评测无从判定；没有确认，一次系统性错误就能毁掉全部产出；没有评测，你连自己在变好还是变坏都不知道。

这也是我觉得“没有评测的 agent 只是一个演示”这句话值得反复说的原因。演示证明的是可能性，工程要证明的是可重复性。

最后留个话头：本文讲的都是单个 agent 的闭环。多个 agent 协作时，边界怎么切、上下文怎么隔离、评测怎么归因，是另一套问题，我目前没有足够的实践来写，等有了再补。
